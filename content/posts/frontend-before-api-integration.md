프론트엔드 화면이 준비되면 API 주소를 넣는 것만으로 연동이 끝날 것처럼 느껴진다. 실제 프로젝트에서는 요청을 보내기 전에 확인해야 할 기준이 더 많았다.

## 성공 응답보다 실패 응답을 먼저 확인했다

성공했을 때 보여 줄 화면은 비교적 명확하다. 반면 인증이 만료됐거나 입력값이 잘못됐을 때의 처리가 정해지지 않으면 페이지마다 다른 방식으로 오류를 보여 주게 된다.

연동 전에 아래 항목을 먼저 확인했다.

- 공통 응답이 `resultType`, `message`, `data` 구조인지
- 인증 실패 시 사용하는 상태 코드와 에러 코드
- 빈 배열과 `null`을 각각 언제 반환하는지
- 날짜가 문자열이라면 어떤 형식인지
- 필수 값과 선택 값이 무엇인지

이 기준을 요청 함수에서 한 번 정리하면 화면 컴포넌트는 성공 데이터와 사용자 안내에 집중할 수 있다.

## 개발 환경과 운영 환경의 주소를 분리했다

로컬에서는 프론트엔드와 백엔드가 서로 다른 포트를 사용한다. 운영 환경에서는 같은 도메인의 상대 경로를 사용할 수도 있다.

환경마다 주소를 코드에 직접 쓰는 대신 환경변수와 프록시 설정의 책임을 구분했다.

```text
로컬 개발: 개발 서버가 백엔드 주소로 프록시
운영 배포: 같은 origin의 /api 경로 사용
```

환경 설정을 바꿀 때는 실제 네트워크 요청이 어느 주소로 나가는지 개발자 도구에서 함께 확인해야 한다. 주석의 설명과 실행 결과가 항상 같다고 가정하면 안 된다.

## 인증 정보의 저장 위치를 한곳에서 관리했다

로그인 이후 모든 요청에 토큰이 필요하다면 각 페이지에서 직접 헤더를 만들지 않는다. 공통 API 클라이언트에서 토큰을 읽고 `Authorization` 헤더를 붙이도록 정리했다.

이렇게 하면 토큰 형식이 바뀌거나 만료 처리 로직이 추가돼도 수정 범위를 줄일 수 있다.

## 배운 점

API 연동은 프론트엔드 코드를 백엔드에 연결하는 마지막 단계가 아니라, 서로 다른 기준을 하나로 맞추는 과정이었다. 엔드포인트만 보는 대신 요청, 응답, 오류, 인증, 환경 설정을 한 묶음으로 확인해야 안정적으로 연결할 수 있었다.
