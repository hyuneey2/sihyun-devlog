## 회원가입 경로에 따라 `role`이 달라진 문제 해결 과정

Swagger에서는 회원가입과 로그인이 정상적으로 동작했지만, 프론트엔드에서 가입한 계정으로 로그인하면 오류가 발생했습니다. 로그인 로직이 아니라 사용자 생성 시점에 `role`이 누락된 문제를 확인하고 수정한 기록입니다.

## 문제 상황

회원가입 API를 프론트엔드에 연동한 뒤 실행 경로에 따라 결과가 달라졌습니다.

```text
Swagger에서 회원가입
→ 로그인 성공

프론트엔드에서 회원가입
→ 로그인 실패
```

같은 백엔드 API를 호출하고 있었기 때문에 처음에는 원인을 찾기 어려웠습니다. Swagger에서는 회원가입과 로그인이 모두 정상적으로 처리됐고, 기존 계정도 로그인할 수 있었습니다.

프론트엔드에서 만든 계정만 실패한다는 점을 기준으로 로그인 요청보다 회원가입 과정부터 확인했습니다.

## 처음에는 로컬 환경을 의심했다

프론트엔드를 로컬에서 실행하고 있었기 때문에 로컬 DB 설정이 없어서 발생한 문제라는 의견이 있었습니다.

하지만 당시 구조는 로컬 프론트엔드가 배포된 백엔드 API를 호출하는 방식이었습니다.

```text
로컬 프론트엔드
→ 배포된 백엔드
→ 서버 DB
```

프론트엔드가 로컬에서 실행된다는 이유만으로 MySQL을 설치할 필요는 없습니다. 로컬 DB는 백엔드까지 로컬에서 실행할 때 필요합니다.

Swagger와 프론트엔드 모두 같은 배포 서버를 사용하고 있었기 때문에 DB 연결보다 두 요청 사이의 차이를 확인해야 했습니다.

## 로그인 오류의 원인은 회원가입에 있었다

기존 계정과 Swagger에서 만든 계정은 로그인할 수 있었지만, 프론트엔드에서 만든 계정만 로그인할 수 없었습니다.

로그인 로직 자체가 문제라면 모든 계정에서 같은 오류가 발생해야 합니다. 특정 경로에서 생성한 계정만 실패한다는 것은 저장된 사용자 데이터가 다르다는 뜻이었습니다.

확인 결과 프론트엔드에서 가입한 사용자의 `role`이 `null`로 저장되고 있었습니다.

```text
프론트엔드 회원가입
→ role이 없는 요청 전송
→ role을 지정하지 않고 User 생성
→ DB에 role=null 저장
→ 로그인 과정에서 role 사용
→ 오류 발생
```

오류는 로그인할 때 나타났지만 잘못된 상태는 회원가입 시점에 만들어졌습니다.

## Swagger에서는 왜 정상적으로 동작했는가

일반 회원가입으로 생성되는 사용자의 기본 권한은 `USER`입니다.

Swagger에서는 테스트 요청에 `role`을 직접 넣었거나, 역할을 지정하는 생성 경로를 사용했던 것으로 확인했습니다.

```json
{
  "loginId": "user1",
  "password": "12345678",
  "role": "USER"
}
```

반면 프론트엔드 회원가입 요청에는 역할이 포함되지 않았습니다.

```json
{
  "loginId": "user1",
  "password": "12345678"
}
```

프론트엔드에서 역할을 보내지 않는 것은 정상입니다. 사용자가 회원가입 요청의 `role`을 직접 지정할 수 있다면 다음과 같이 관리자 계정 생성을 시도할 수 있기 때문입니다.

```json
{
  "loginId": "user1",
  "password": "12345678",
  "role": "ADMIN"
}
```

일반 회원의 역할은 클라이언트 입력이 아니라 서버 정책으로 결정해야 합니다.

문제는 프론트엔드가 역할을 보내지 않은 것이 아니라, 백엔드에서도 역할을 지정하지 않은 채 사용자를 생성한 것이었습니다.

## 필드 초기값만으로는 부족했던 이유

엔티티 필드에 기본값을 선언하면 역할이 자동으로 설정될 것으로 생각할 수 있습니다.

```java
@Enumerated(EnumType.STRING)
private UserRole role = UserRole.USER;
```

하지만 Lombok의 `@Builder`를 통해 객체를 생성하는 경우에는 생성 방식에 따라 필드 초기값이 보장되지 않을 수 있습니다.

```java
User user = User.builder()
    .loginId(request.loginId())
    .password(encodedPassword)
    .build();
```

Builder에서 `role`을 지정하지 않으면 `null`이 들어갈 수 있습니다. 생성 경로에 따라 기본값이 적용되기도 하고 적용되지 않기도 하는 구조는 오류를 찾기 어렵게 만듭니다.

`@Builder.Default`를 추가하는 방법도 검토할 수 있습니다.

```java
@Builder.Default
@Enumerated(EnumType.STRING)
private UserRole role = UserRole.USER;
```

이 방식은 Builder에서도 필드 초기값을 유지합니다. 다만 이번 문제에서는 일반 회원가입의 권한 정책을 생성 코드에 직접 드러내는 방식이 더 적합하다고 판단했습니다.

## 회원 생성 시 `USER`를 명시하도록 수정

일반 회원가입으로 생성되는 사용자는 항상 `USER` 권한을 가져야 합니다.

회원가입 서비스에서 `User` 엔티티를 생성할 때 역할을 직접 지정하도록 수정했습니다.

```java
User user = User.builder()
    .loginId(request.loginId())
    .password(encodedPassword)
    .role(UserRole.USER)
    .build();
```

수정 후에는 프론트엔드 요청에 `role`이 없어도 서버가 기본 권한을 결정합니다.

```text
회원가입 요청
→ 요청값 검증
→ 비밀번호 암호화
→ role을 USER로 지정
→ 사용자 저장
```

## 생성 코드에서 역할을 지정한 이유

엔티티의 기본값에만 의존하지 않고 생성 코드에서 역할을 명시한 이유는 생성 규칙을 분명하게 만들기 위해서입니다.

일반 회원가입에서 `USER`를 부여하는 것은 단순한 초기값 설정이 아니라 서비스 정책입니다.

```java
.role(UserRole.USER)
```

이 코드가 있으면 해당 회원가입 경로로 생성되는 사용자의 권한을 바로 확인할 수 있습니다. 프론트엔드 요청 형식이나 Builder 동작 방식이 달라져도 일반 사용자의 역할은 유지됩니다.

역할을 관리하는 흐름도 구분할 수 있습니다.

```text
일반 회원가입
→ USER로 생성

관리자 권한 부여
→ 인증된 관리자가 별도 기능으로 변경
```

권한을 생성하는 책임을 서버가 가지게 되면서 클라이언트 요청에 대한 의존도도 줄어들었습니다.

## `role=null`이 로그인 실패로 이어진 이유

DB가 `null`을 허용하고 있었다면 회원가입 자체는 성공할 수 있습니다. 문제는 로그인 후 인증 정보를 생성하는 과정에서 발생합니다.

JWT에 역할을 넣는 코드가 다음과 같다면,

```java
claims.put("role", user.getRole().name());
```

`user.getRole()`이 `null`인 상태에서 `.name()`을 호출할 때 오류가 발생합니다.

Spring Security 권한 객체를 만드는 과정에서도 같은 문제가 생길 수 있습니다.

```java
new SimpleGrantedAuthority(user.getRole().name());
```

따라서 로그인 실패만 보면 JWT나 인증 로직의 문제처럼 보이지만, 실제 원인은 권한 없이 저장된 사용자 데이터였습니다.

## 애플리케이션 코드만 수정하면 충분한가

회원가입 서비스에서 `USER`를 지정하면 해당 생성 경로의 문제는 해결됩니다. 다만 다른 서비스나 테스트 코드에서 `User`를 직접 생성할 가능성은 남아 있습니다.

다른 경로에서 역할을 빠뜨리면 다시 `null`이 저장될 수 있습니다. 이를 막으려면 DB 제약 조건도 함께 적용하는 편이 안전합니다.

```java
@Enumerated(EnumType.STRING)
@Column(nullable = false)
private UserRole role;
```

역할 보장은 다음과 같이 나눌 수 있습니다.

```text
회원가입 서비스
→ 일반 사용자의 role을 USER로 결정

엔티티와 DB
→ role=null 상태의 저장 차단
```

회원가입 서비스는 비즈니스 규칙을 보장하고, DB 제약 조건은 잘못된 데이터가 저장되는 것을 마지막 단계에서 막습니다.

## 기존 데이터도 정리해야 했다

코드를 수정해도 이미 `role=null`로 저장된 계정은 자동으로 변경되지 않습니다.

기존 계정으로 다시 로그인하면 같은 오류가 발생할 수 있기 때문에 테스트 데이터를 삭제하고 다시 가입하거나 역할 값을 수정해야 합니다.

```sql
SELECT *
FROM users
WHERE role IS NULL;
```

대상을 확인한 뒤 다음과 같이 수정할 수 있습니다.

```sql
UPDATE users
SET role = 'USER'
WHERE role IS NULL;
```

새 코드가 정상적으로 동작하는지 확인할 때는 기존 계정이 아니라 수정 후 새로 생성한 계정으로 테스트해야 합니다.

## 수정 결과

회원 생성 시 역할을 명시한 뒤 Swagger와 프론트엔드에서 각각 새로운 계정을 생성했습니다.

```text
Swagger 회원가입
→ role=USER 저장
→ 로그인 성공

프론트엔드 회원가입
→ role=USER 저장
→ 로그인 성공
```

실행 경로와 관계없이 같은 사용자 데이터가 생성됐고, 로그인 과정에서도 역할 정보를 정상적으로 사용할 수 있었습니다.

## 정리

프론트엔드에서 가입한 계정만 로그인에 실패해 처음에는 로컬 환경과 DB 설정을 의심했습니다. 하지만 프론트엔드는 배포된 백엔드와 서버 DB를 사용하고 있었고, 문제는 실행 환경이 아니라 사용자 생성 과정에 있었습니다.

프론트엔드 요청에는 `role`이 없었고, 백엔드에서도 역할을 지정하지 않아 `role=null`인 사용자가 저장됐습니다. 로그인 과정에서 JWT나 권한 객체를 만들기 위해 역할을 사용하면서 오류가 발생했습니다.

일반 회원가입 시 역할을 명시하도록 수정했습니다.

```java
User user = User.builder()
    .loginId(request.loginId())
    .password(encodedPassword)
    .role(UserRole.USER)
    .build();
```

권한처럼 서버 정책으로 결정해야 하는 값은 클라이언트 입력이나 객체 생성 방식의 암묵적인 기본값에 맡기지 않는 편이 안전합니다. 생성 시점에 값을 명시하고, DB에서도 `null`을 제한해야 생성 경로가 추가되더라도 같은 문제를 막을 수 있습니다.
