Node.js로 API를 만들기 전에 데이터가 어떤 구조로 저장되는지부터 정리했다. API의 요청과 응답은 결국 데이터베이스의 구조를 바탕으로 만들어지기 때문에, 테이블 관계가 불분명하면 기능을 추가할수록 쿼리와 서비스 로직도 함께 복잡해진다.

## MySQL의 기본 구조

MySQL은 관계형 데이터베이스 관리 시스템이다. 데이터는 행과 열로 이루어진 테이블에 저장되고, 하나의 데이터베이스 안에 여러 테이블을 둘 수 있다.

```text
MySQL Server
└─ Database
   ├─ User Table
   ├─ Store Table
   └─ Mission Table
```

테이블을 만들 때는 각 컬럼의 데이터 타입과 제약 조건을 함께 정한다.

```sql
CREATE TABLE user (
  id BIGINT NOT NULL AUTO_INCREMENT,
  email VARCHAR(100) NOT NULL,
  name VARCHAR(50) NOT NULL,
  PRIMARY KEY (id),
  UNIQUE (email)
);
```

- `PRIMARY KEY`: 각 행을 유일하게 식별한다.
- `FOREIGN KEY`: 다른 테이블의 기본 키를 참조한다.
- `NOT NULL`: 값이 반드시 있어야 한다.
- `UNIQUE`: 같은 값의 중복 저장을 막는다.
- `AUTO_INCREMENT`: 새 행이 추가될 때 식별값을 자동으로 증가시킨다.

처음에는 컬럼의 의미만 생각했지만, 실제 설계에서는 값이 없을 수 있는지와 중복을 허용할지도 함께 결정해야 했다. 이 조건들이 이후 입력 검증과 오류 응답의 기준이 된다.

## 관계를 테이블로 표현하는 방법

ERD는 엔티티와 속성, 엔티티 사이의 관계를 시각적으로 표현한 다이어그램이다. 화면에 필요한 데이터를 바로 테이블로 옮기기보다 먼저 핵심 대상을 엔티티로 분리했다.

### 1:1 관계

한 사용자에게 하나의 프로필만 존재한다면 두 테이블은 1:1 관계다. 프로필 테이블이 사용자 ID를 외래 키로 참조하고, 중복을 허용하지 않도록 설정할 수 있다.

### 1:N 관계

한 가게가 여러 미션을 가질 수 있다면 가게와 미션은 1:N 관계다. N에 해당하는 미션 테이블에 `store_id`를 둔다.

```text
Store 1 ─── N Mission
```

### N:M 관계

한 사용자가 여러 미션에 참여하고, 하나의 미션에도 여러 사용자가 참여할 수 있다면 사용자와 미션은 N:M 관계다. 관계를 직접 저장하지 않고 중간 테이블로 해소한다.

```text
User 1 ─── N UserMission N ─── 1 Mission
```

`UserMission`에는 두 테이블의 외래 키뿐 아니라 참여 상태, 시작일, 완료일처럼 관계 자체가 가지는 정보도 저장할 수 있다.

## 여러 테이블의 데이터를 조회하는 JOIN

테이블을 역할별로 분리하면 조회할 때 다시 연결해야 한다. `JOIN`은 공통 키를 기준으로 여러 테이블의 데이터를 하나의 결과로 가져오는 방법이다.

```sql
SELECT
  u.name,
  m.title,
  um.status
FROM user_mission um
JOIN user u ON u.id = um.user_id
JOIN mission m ON m.id = um.mission_id
WHERE um.status = 'IN_PROGRESS';
```

- `INNER JOIN`: 양쪽 조건이 일치하는 행만 조회한다.
- `LEFT JOIN`: 왼쪽 테이블의 행은 모두 유지하고, 일치하지 않는 오른쪽 값은 `NULL`로 반환한다.
- `RIGHT JOIN`: 오른쪽 테이블을 기준으로 모든 행을 유지한다.
- `SELF JOIN`: 같은 테이블을 서로 다른 별칭으로 두고 연결한다.

목록에 반드시 보여야 하는 기준 데이터가 무엇인지에 따라 `INNER JOIN`과 `LEFT JOIN`을 구분해야 했다. 단순히 테이블을 연결하는 문법보다 결과에서 누락되어도 되는 행을 먼저 판단하는 일이 중요했다.

## 쿼리 안에서 값을 구하는 서브쿼리

서브쿼리는 SQL문 안에 포함된 또 다른 `SELECT`문이다. 조건값을 구하거나 임시 조회 결과를 테이블처럼 사용할 때 활용한다.

```sql
SELECT name
FROM user
WHERE id IN (
  SELECT user_id
  FROM user_mission
  WHERE status = 'COMPLETED'
);
```

사용 위치에 따라 역할이 달라진다.

- `WHERE`: 비교하거나 필터링할 값을 만든다.
- `FROM`: 조회 결과를 임시 테이블처럼 사용한다.
- `SELECT`: 각 행에 표시할 단일 값을 계산한다.

서브쿼리는 복잡한 조건을 단계별로 읽기 쉽게 만들 수 있지만, 같은 조회가 반복되면 성능에 영향을 줄 수 있다. JOIN과 서브쿼리 중 무엇이 무조건 좋은 것이 아니라 결과의 형태와 실행 계획을 기준으로 선택해야 한다.

## 정규화와 반정규화

정규화는 데이터 중복을 줄이고 수정·삭제 과정에서 생기는 이상 현상을 막기 위해 테이블을 분리하는 과정이다. 사용자 정보와 미션 정보를 하나의 테이블에 반복해서 저장하지 않고 각각 관리하는 것이 대표적이다.

반정규화는 조회 성능이나 구현 단순화를 위해 일부 중복을 허용하는 방식이다. 다만 데이터 일관성을 유지할 책임이 추가되므로, 먼저 정규화된 구조를 만든 뒤 실제 병목이 확인될 때 검토하는 편이 안전하다.

## 요구사항을 ERD로 바꾸며 세운 기준

지역별 가게와 방문 미션, 사용자 참여와 완료 기록이 있는 서비스를 기준으로 다음 엔티티를 분리했다.

- 사용자 `User`
- 지역 `Region`
- 가게 `Store`
- 미션 `Mission`
- 사용자별 미션 `UserMission`
- 리뷰 `Review`

이때 화면에 보이는 문장을 그대로 테이블 이름으로 옮기지 않고, 각 데이터가 독립적으로 존재할 수 있는지와 누구에게 속하는지를 먼저 확인했다. 특히 사용자별 미션 상태는 사용자나 미션 한쪽의 속성이 아니라 두 엔티티 사이의 관계 정보이므로 중간 테이블에 두는 것이 자연스러웠다.

첫 주차에서 얻은 기준은 단순했다. API를 만들기 전에 데이터의 주인과 관계를 먼저 정하고, 중복과 선택값을 데이터베이스 제약 조건으로 표현해야 이후 코드의 예외 처리가 분명해진다.
