## 로그인 응답에 없는 사용자 역할을 JWT에서 확인한 과정

로그인 후 사용자 역할에 따라 화면을 나누는 과정에서 발생한 문제를 해결한 기록입니다.

서비스에서는 관리자와 일반 사용자가 사용할 수 있는 기능이 다릅니다.

```text
ADMIN
- 예배 등록
- 공지사항 작성
- 관리자 페이지 접근

USER
- 예배 및 공지사항 조회
- 일반 사용자 페이지 접근
```

로그인이 끝나면 현재 사용자가 `ADMIN`인지 `USER`인지 확인해 이동할 페이지와 표시할 메뉴를 결정해야 했습니다. 하지만 로그인 응답에는 역할 정보가 없었습니다.

## 문제 상황

백엔드의 로그인 응답은 Access Token과 Refresh Token만 반환했습니다.

```java
public record LoginResponse(
    String accessToken,
    String refreshToken
) {
}
```

프론트엔드가 받는 응답도 다음과 같았습니다.

```json
{
  "accessToken": "...",
  "refreshToken": "..."
}
```

사용자 ID, 이름, 역할은 포함되지 않았습니다.

처음에는 로그인 응답에 `role`이 없기 때문에 로그인한 사용자의 권한을 확인할 수 없다고 판단했습니다.

```text
로그인 성공
→ 토큰 수신
→ 사용자 역할을 알 수 없음
→ 이동할 화면을 결정할 수 없음
```

## 왜 혼란이 생겼는가

백엔드에는 관리자용 사용자 조회 API가 있었습니다. 해당 API를 호출하면 사용자의 `role`을 확인하거나 변경할 수 있었습니다.

하지만 이 API는 관리자가 다른 사용자를 관리하기 위한 기능입니다. 현재 로그인한 사용자의 역할을 확인하기 위한 API와는 목적이 다릅니다.

로그인 직후에는 아직 현재 사용자가 관리자인지 알 수 없습니다. 이 상태에서 관리자 전용 API를 호출해 역할을 확인하는 구조는 순서가 맞지 않습니다.

```text
관리자 API를 호출하려면 관리자 권한이 필요함
→ 현재 사용자가 관리자인지 먼저 확인해야 함
→ 관리자 여부를 확인하기 위해 관리자 API를 호출할 수는 없음
```

회원가입 시 기본 역할이 `USER`로 설정되고 관리자가 이후 역할을 변경할 수 있다는 설명도 로그인 후 역할을 확인하는 문제와는 별개였습니다.

역할을 어떻게 생성하거나 변경하는지와 현재 로그인한 사용자의 역할을 어떻게 확인하는지를 구분하지 못해 논의가 엇갈렸습니다.

## 먼저 검토한 방법: 사용자 정보 API 호출

로그인 후 현재 사용자 정보를 조회하는 API를 호출하는 방법을 먼저 검토했습니다.

```text
로그인 요청
→ Access Token 발급
→ 현재 사용자 정보 조회
→ Role 확인
→ 화면 이동
```

이 방식은 서버에 저장된 최신 사용자 정보를 받을 수 있습니다. 역할뿐 아니라 이름, 사용자 ID 등 화면에 필요한 정보도 함께 가져올 수 있습니다.

다만 당시에는 로그인한 사용자 본인의 정보를 조회하는 `/me` 형태의 API가 명확하게 준비되어 있지 않았습니다. 역할 하나를 확인하기 위해 새 API를 추가하면 백엔드 수정과 추가 요청이 필요했습니다.

관리자용 사용자 조회 API를 대신 사용하는 것도 적절하지 않았습니다. 해당 API는 관리자 권한이 필요한 기능이며 현재 사용자 확인을 위한 API가 아니기 때문입니다.

## 로그인 응답에 Role을 추가하는 방법

로그인 응답에 역할을 직접 포함하는 방법도 검토했습니다.

```java
public record LoginResponse(
    String accessToken,
    String refreshToken,
    String role
) {
}
```

프론트엔드에서는 응답에 포함된 역할을 바로 사용할 수 있습니다.

```ts
const { accessToken, refreshToken, role } = response.data;
```

구조가 단순하고 로그인 결과에 필요한 정보가 명확하게 드러난다는 장점이 있습니다.

하지만 백엔드의 응답 DTO와 로그인 로직을 수정해야 했습니다. 확인 과정에서 Access Token에 이미 역할 정보가 들어 있다는 사실도 알게 됐습니다.

같은 값을 로그인 응답과 JWT에 중복해서 담기보다 기존 토큰의 Claim을 활용할 수 있는지 확인했습니다.

## JWT Claim 확인

백엔드의 JWT 생성 코드는 사용자 정보를 Claims에 추가하고 있었습니다.

```java
return Jwts.builder()
    .setIssuer(jwtProperties.getIssuer())
    .setSubject(subject)
    .addClaims(claims)
    .setIssuedAt(iat)
    .setExpiration(exp)
    .signWith(key, SignatureAlgorithm.HS256)
    .compact();
```

`claims`에는 사용자 역할이 포함되어 있었습니다.

Access Token의 Payload는 다음과 같은 정보를 가질 수 있습니다.

```json
{
  "sub": "1",
  "role": "ADMIN",
  "iat": 1785430000,
  "exp": 1785433600
}
```

로그인 응답에 `role` 필드가 따로 없어도 토큰 내부에는 역할 정보가 있었습니다.

문제는 역할 정보가 없는 것이 아니라 로그인 응답 DTO만 확인하고 JWT Payload를 확인하지 않았던 것입니다.

## JWT 디코딩을 선택한 이유

현재 구조에서는 프론트엔드에서 Access Token을 디코딩하는 방법을 선택했습니다.

선택한 이유는 다음과 같습니다.

첫째, 로그인 직후 역할을 확인할 수 있습니다.

```text
로그인 성공
→ Access Token 수신
→ Payload 디코딩
→ Role 확인
→ 화면 이동
```

별도의 사용자 정보 요청을 기다리지 않고 관리자와 일반 사용자 화면을 나눌 수 있습니다.

둘째, 백엔드 응답 구조를 변경하지 않아도 됩니다. 역할 정보가 이미 JWT Claim에 포함되어 있으므로 기존 로그인 API를 그대로 사용할 수 있습니다.

셋째, 역할 하나를 확인하기 위한 추가 API 요청이 필요하지 않습니다. 현재 사용자 정보 전체가 필요한 상황이 아니라 로그인 직후 화면을 나누는 것이 목적이었기 때문에 토큰에 포함된 값을 활용했습니다.

이 방식은 역할 정보가 이미 JWT에 존재하고, 로그인 직후의 화면 분기에만 필요한 현재 구조에 맞았습니다.

## 프론트엔드 적용

JWT Payload를 읽기 위해 `jwt-decode`를 설치했습니다.

```bash
npm install jwt-decode
```

토큰에 포함된 값의 타입을 정의했습니다.

```ts
type UserRole = 'ADMIN' | 'USER';

interface AccessTokenPayload {
  sub: string;
  role: UserRole;
  iat: number;
  exp: number;
}
```

로그인 성공 후 Access Token을 디코딩했습니다.

```ts
import { jwtDecode } from 'jwt-decode';

const payload = jwtDecode<AccessTokenPayload>(accessToken);
const role = payload.role;
```

추출한 역할에 따라 이동할 페이지를 결정했습니다.

```ts
if (role === 'ADMIN') {
  navigate('/admin');
} else {
  navigate('/');
}
```

로그인 흐름은 다음과 같이 정리됐습니다.

```text
로그인 요청
→ Access Token과 Refresh Token 수신
→ Access Token Payload 디코딩
→ Role 추출
→ 역할별 화면으로 이동
```

## JWT 디코딩 방식의 한계

JWT를 디코딩하면 Payload를 읽을 수 있지만 토큰의 유효성을 검증할 수는 없습니다.

`jwt-decode`는 Base64 형식의 Payload를 해석합니다. 서버의 비밀키로 서명을 검증하지 않기 때문에 디코딩한 값만으로 접근 권한을 보장할 수 없습니다.

따라서 프론트엔드에서 추출한 역할은 화면을 구성하는 용도로만 사용했습니다.

```text
프론트엔드
- 역할별 초기 화면 이동
- 관리자 메뉴 표시
- 관리자 버튼 노출 여부 결정

백엔드
- Access Token 서명 검증
- 실제 사용자 역할 확인
- 관리자 API 접근 허용 또는 거부
```

사용자가 브라우저 상태를 변경하거나 프론트엔드 코드를 우회해 관리자 API를 직접 호출할 수 있습니다. 버튼을 숨기거나 관리자 페이지 진입을 막는 것만으로는 API를 보호할 수 없습니다.

실제 권한 검사는 백엔드에서 처리해야 합니다.

```http
HTTP/1.1 403 Forbidden
```

## 토큰에 저장된 역할이 오래될 수 있는 문제

JWT에 포함된 역할은 토큰이 발급된 시점의 값입니다.

예를 들어 관리자가 사용자의 역할을 `USER`에서 `ADMIN`으로 변경해도 기존 Access Token에는 이전 역할이 남아 있을 수 있습니다.

```text
토큰 발급 시점
role: USER

서버의 역할 변경
USER → ADMIN

기존 토큰
role: USER 유지
```

새 토큰을 발급받기 전까지 프론트엔드에는 변경된 역할이 반영되지 않을 수 있습니다.

반대로 관리자 역할이 회수된 경우에도 기존 토큰의 만료 전까지 Payload에는 `ADMIN`이 남을 수 있습니다. 백엔드가 토큰에 포함된 역할만 신뢰하는 구조라면 권한 변경이 즉시 반영되지 않는 문제도 생길 수 있습니다.

역할 변경이 자주 발생하거나 변경 내용을 즉시 반영해야 한다면 로그인 후 사용자 정보 API를 호출하거나, 요청마다 서버의 현재 권한을 조회하는 구조를 검토해야 합니다.

이번 프로젝트에서는 관리자 역할을 자주 변경하지 않고 Access Token의 만료 시간이 정해져 있어 JWT Claim을 사용했습니다.

## 프론트엔드가 JWT 구조에 의존하는 문제

JWT에서 역할을 직접 꺼내 사용하면 프론트엔드가 백엔드의 Claim 구조에 의존하게 됩니다.

백엔드에서 Claim 이름을 `role`에서 `authorities`로 변경하거나 값의 형식을 수정하면 프론트엔드 코드도 함께 바꿔야 합니다.

```json
{
  "role": "ADMIN"
}
```

```json
{
  "authorities": ["ROLE_ADMIN"]
}
```

로그인 응답에 역할을 명시적으로 포함하거나 `/me` API를 사용하면 토큰 내부 구조를 프론트엔드가 알 필요가 없습니다.

JWT Claim 디코딩은 현재 구조를 빠르게 연결하는 데 적합했지만, 프론트엔드와 인증 토큰의 결합이 생긴다는 한계가 있습니다.

## 이후 구조를 확장한다면

로그인 직후 역할만 필요한 현재 단계에서는 JWT 디코딩으로 처리했습니다.

사용자 이름, 프로필, 소속 등 로그인 사용자 정보가 더 필요해진다면 `/me` API를 추가하는 편이 적합합니다.

```text
POST /auth/login
→ 토큰 발급

GET /users/me
→ 현재 사용자 ID
→ 이름
→ 역할
→ 프로필 정보
```

이 구조에서는 JWT를 인증 수단으로 사용하고, 화면에 필요한 사용자 정보는 서버에서 조회할 수 있습니다.

역할 변경도 새로 조회한 사용자 정보에 반영되므로 토큰 Payload만 사용하는 방식보다 최신 상태를 유지하기 쉽습니다.

## 정리

로그인 응답에 토큰만 포함되어 있어 로그인한 사용자의 역할을 확인할 수 없다고 생각했습니다.

관리자용 사용자 조회 API가 존재했지만 현재 로그인한 사용자의 권한을 확인하기 위한 API는 아니었습니다. 관리자 API를 호출하기 전에 관리자 여부를 알아야 하므로 역할 확인 수단으로 사용할 수 없었습니다.

로그인 응답에 `role`을 추가하는 방법과 현재 사용자 조회 API를 추가하는 방법을 검토했지만, Access Token의 Claim에 역할이 이미 포함되어 있었습니다.

현재 구조에서는 다음 이유로 JWT 디코딩을 선택했습니다.

```text
- 로그인 직후 역할을 확인할 수 있음
- 추가 API 요청이 필요하지 않음
- 기존 백엔드 응답을 변경하지 않아도 됨
- JWT에 이미 포함된 정보를 활용할 수 있음
```

다만 디코딩은 권한 검증이 아니며, 토큰 발급 후 변경된 역할을 즉시 반영하지 못합니다. 프론트엔드가 JWT Claim 구조에 의존한다는 한계도 있습니다.

따라서 프론트엔드에서는 화면 분기에만 사용하고 실제 API 권한은 백엔드에서 검증하도록 구분했습니다. 사용자 정보가 더 필요하거나 역할 변경을 바로 반영해야 한다면 `/me` API를 사용하는 구조가 더 적합합니다.
