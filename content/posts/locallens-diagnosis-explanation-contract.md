2026년 10월 #10과 #13은 진단·지도·결과·보고서의 설명 불일치를 정리했다. 숫자가 화면에 정상으로 표시된다는 것만으로 데이터가 정확하게 전달되지는 않았다. 같은 비율이라도 대상 주민과 시설이 다르면 다른 정책 판단을 만들 수 있었다.

## 시설을 바꿨는데 tooltip은 계속 응급실이었다

#10 이전 지도 시간 레이어 tooltip은 '응급실까지 약 N분'으로 고정되어 있었다. 선택 시설에 따라 실제 격자 값이 달라져도 문구는 같았다. 변경 후 CAR_TARGETS에서 현재 선택의 짧은 이름을 가져와 표시했다.

```text
수정 전: 선택 = 동네 의원 / tooltip = 응급실까지 N분
수정 후: 선택 = 동네 의원 / tooltip = 동네 의원까지 N분
```

범례와 마을 카드에도 같은 시설 이름을 사용해야 한다. 화면마다 문구를 따로 고치면 사용자는 서로 다른 계산을 한 것으로 읽을 수 있다. #13은 판정 사유의 용어도 선택 시설에 맞춰 통일했다.

## '30분 밖 주민'의 분모는 누구인가

진단 응급 카드는 선택한 나이대의 인구로 센다. 서버 지표 E30은 전체 주민 기준이다. 둘 다 30분을 쓰더라도 80세 이상과 전체 주민의 비율은 같을 이유가 없다.

수정 전에는 이 차이가 드러나지 않아 서로 다른 숫자가 오류처럼 보이거나 같은 의미로 인용될 수 있었다. #10은 카드에 선택 나이대를, E30 설명에는 전체 주민 기준을 표시했다. 미래 예측값이 없는 나이대는 future를 null로 다루며 '0%'로 그리지 않도록 타입과 표시 조건도 수정했다. 자료 없음과 달성률 0은 다른 상태다.

## 자가용 탐색값을 서버의 정책 조건에 섞지 않았다

자가용 탭에서 시간을 바꾸는 것은 그 화면의 탐색이다. 기존에는 서버 criteria.carMinutes를 직접 바꿔 후속 계산에도 영향이 갈 수 있었다. #10에서 carView라는 화면 값을 따로 두고 결과·보고서는 서버 기준으로 계산함을 안내했다.

이 구분이 없으면 사용자는 지도에서 바꾼 조건으로 예산 대안이 계산된다고 생각할 수 있다. 반대로 지도용 선택을 모두 서버 입력으로 보내도 API가 지원하는 정책 모델과 달라진다. #13의 대중교통 설명·슬라이더 정리는 실제 판정에 쓰는 조건만 조절하는 문제와도 연결된다.

## 비율과 경계값도 설명의 계약이다

원격진료 효과는 내부의 0~1 값과 화면의 퍼센트를 구분하고 반올림을 맞췄다. '10% 입력'과 0.1을 서로 바꿔 전달하는 경계에서 100배 차이가 생기지 않아야 한다. effect를 단순 시설 수 증가처럼 설명하는 것도 coverage 비율이라는 모델과 다르다.

첫차 판정은 '정오 전'이다. #13은 정확히 720분인 12:00을 통과시키던 경계를 서버의 미만 조건과 맞췄다. 현재 코드의 조건은 다음과 같다.

```ts
b.firstToTownMin != null && b.firstToTownMin < FIRST_BUS_LIMIT
// FIRST_BUS_LIMIT = 720
```

읍내 마을의 0분 값은 첫차 없음과 같지 않고, 추정 첫차 자료 역시 실제 시간표와 구분해야 한다. 데이터의 특별한 값과 자연어를 연결하는 단계도 검증 대상이었다.

## 변경 결과를 확인한 범위

#10은 타입 검사, 테스트 47개, 프로덕션 빌드와 로컬 주요 화면 확인을 기록했다. 원격진료 입력 중 커서 이동은 후속 개선 가능 사항으로 남겼다. #13은 추가 일관성 수정과 공유 설정 복원, 자동 저장 코드 통합을 포함한다. 이 기록을 전체 운영 데이터의 정확성 검증으로 확대하지 않는다.

#14의 데이터 분석 기준 페이지 연결까지 이어서 보면, 설명을 더 길게 쓰기보다 어떤 값의 기준을 어디에서 확인할 수 있는지 고정하는 일이었다. 계산식과 사용자에게 보이는 문장 모두 같은 입력 계약을 가리켜야 했다.
