2026년 10월 #13은 공유 링크에 진단 설정을 포함하고 복원을 개선했다. 예산과 목표만 같은 링크라도 기준 시간·공급수단·단가가 다르면 대안이 달라진다. 무엇을 링크로 옮길지와 어디까지 같은 결과를 기대할 수 있는지를 함께 정해야 했다.

## 상태 전체를 JSON으로 넣지 않았다

shareQuery는 계산에 필요한 State의 일부를 명시적인 query key로 옮긴다. 서비스·나이대·예산·목표·선택안 외에 자가용·걷기·운행 기준, 허용 공급수단, 수단별 설치비·연 운영비·수명, 원격 효과와 순회 주당 횟수가 포함된다.

```text
s/a/b/t/p: 서비스·나이대·예산·목표·선택안
cm/sw/dr: 접근 기준
sup: 공급수단
c_<수단>: 비용·수명
te/tw: 원격 효과·순회 횟수
```

선택 마을 hover, 로딩 상태, 서버 응답, 채팅과 직접 고친 보고서 문단은 담지 않는다. URL은 편집 문서 백업이 아니라 계산 조건의 전달 형식이다.

## 쿼리는 신뢰할 수 있는 State가 아니다

readShare는 현재 State를 바탕으로 유효한 값만 덮는다. 처음 진입할 때는 서버 기본값을 기준으로 하므로 예전 s/a/b/t/p만 가진 링크도 나머지 값을 기본값으로 유지한다.

숫자는 빈 문자열·NaN·Infinity를 거르고 범위와 정수 조건을 확인한다. 예산 0~30억, 목표 0.5~1, 선택안 0~2 정수처럼 각 필드의 실제 계약을 적용한다. Number('')가 0이 되는 것을 그대로 유효한 입력으로 보지 않는다.

공급수단은 하나 이상이어야 하고 모르는 이름이 섞이면 그 목록 전체를 버린다. 수단별 비용 배열도 필드 수와 범위, 수명의 정수 조건이 모두 맞을 때만 사용한다. 원격 효과는 허용 반올림 단위인지도 확인한다. 비슷한 숫자 필드라고 공통 Number 변환 하나로 끝내지 않았다.

## 모르는 값과 예전 값을 처리하는 방법

링크에 없는 값은 현재 기준을 유지한다. 작성할 때도 URLSearchParams를 복사하고 이 기능이 관리하는 key만 지운 뒤 새 값을 넣는다. 다른 query를 무조건 삭제하지 않는다. 같은 URL을 다시 공유할 때 과거 계산값이 중복으로 쌓이지 않도록 자신이 소유한 key만 교체한다.

이 정책은 잘못된 필드 하나 때문에 링크 전체를 거부하는 방식과 다르다. 예산이 잘못되어도 유효한 나이대는 복원할 수 있다. 다만 사용자가 넣은 모든 값이 적용되었다는 뜻은 아니므로 복원된 조건을 화면에서 다시 확인할 수 있어야 한다.

## 같은 링크가 같은 문서는 아니다

지역 자료와 서버 규칙이 바뀌면 같은 입력도 다른 결과를 낼 수 있다. Snapshot 수집일과 서버/추정 여부도 결과 해석에 영향을 준다. 링크는 당시 결과의 불변 스냅샷이나 감사 증빙 파일이 아니다.

보고서 화면은 편집 문단이 있거나 아직 저장하지 않은 글이 있으면 링크 복사 후 '직접 고친 문단은 링크에 담기지 않는다'고 안내한다. 문단은 지역별 브라우저 저장에 남는 별도 경로다. 다른 사람에게 링크만 보내 편집 글까지 전달된다고 기대하게 해서는 안 된다.

## 테스트로 남긴 복원 범위

share.test는 바뀐 기준·공급수단·단가의 왕복, 기본값, 구형 링크, 잘못된 숫자, 공급수단 전체 해제, 다른 query 보존과 편집 문단 제외를 확인한다. 전체 장애 때 미지원 13곳의 공유 주소로 진입하는 경우는 별도 화면·store 테스트가 안내를 확인한다.

이번 글에서는 코드를 근거로 복원 계약을 설명했으며 운영 링크의 장기 재현성을 검증한 것은 아니다. URL로 공유할 수 있는 입력과 영구히 고정해야 할 결과를 구분한 사례다.
