일정 기능을 처음 설계할 때는 반복 일정의 첫 번째 `scheduleId`를 `groupId`로 사용하는 방법을 생각했다. 별도 테이블 없이 일정끼리 묶을 수 있어 단순해 보였다.

하지만 수정과 삭제 범위를 구체적으로 정의하면서 문제가 보이기 시작했다.

## 첫 일정 ID를 그대로 사용했을 때의 문제

반복 일정은 선택한 일정 한 건만 수정하거나, 같은 반복에서 생성된 일정 전체를 수정할 수 있어야 했다. 그런데 그룹을 대표하는 첫 일정이 삭제되면 그룹의 기준도 함께 사라진다.

- 첫 일정이 삭제되면 어떤 값을 새 그룹 ID로 삼을지 정해야 한다.
- 전체 수정 시 반복 조건을 어느 일정에서 읽어야 하는지 모호하다.
- 각 일정에 반복 시작일, 종료일, 요일을 중복 저장하게 된다.
- 단일 일정과 반복 일정의 책임이 한 테이블에 섞인다.

단순히 컬럼 하나를 추가하는 문제가 아니라, **반복 규칙의 생명주기를 어디에서 관리할지** 정해야 했다.

## 반복 그룹을 별도 테이블로 분리했다

최종적으로 `schedule_repeat_group` 테이블을 만들고 반복 규칙을 이곳에 저장했다.

| 테이블 | 책임 |
| --- | --- |
| `schedule` | 실제 날짜에 생성된 일정과 완료 상태 |
| `schedule_repeat_group` | 반복 유형, 시작일, 종료일, 반복 요일 |

각 일정은 nullable한 `groupId`를 가진다. 반복이 없는 일정은 `groupId`가 `null`이고, 반복 일정은 같은 그룹을 참조한다.

이렇게 분리하니 수정·삭제 규칙도 분명해졌다.

### SINGLE

선택한 일정만 수정할 때는 해당 일정을 그룹에서 분리한다. 이후에는 독립된 단일 일정으로 취급한다.

### ALL

그룹 전체를 수정할 때는 반복 그룹의 조건을 갱신하고, 조건에 맞춰 일정 목록을 다시 계산한다.

## 예외 날짜는 생성하지 않는다

매월 31일이나 매년 2월 29일처럼 특정 월·연도에 존재하지 않는 날짜도 정책으로 정해야 했다. 이 경우 다른 날짜로 당겨 생성하지 않고, **해당 회차를 건너뛰는 방식**을 선택했다.

예외를 임의로 보정하면 사용자가 선택하지 않은 날짜에 일정이 생길 수 있기 때문이다.

## 배운 점

처음에는 테이블을 하나 더 만드는 것이 복잡도를 늘린다고 생각했다. 하지만 데이터 구조의 단순함은 테이블 수가 아니라, 각 데이터의 책임이 분명한지에 더 가깝다는 것을 배웠다.

반복 일정 그룹을 분리한 뒤에는 API 응답, 수정 범위, 삭제 트랜잭션까지 같은 기준으로 설명할 수 있었다. 구현 전에 정책과 데이터의 생명주기를 먼저 확인하는 것이 이후의 예외 처리를 줄여 준다는 점도 알게 됐다.
