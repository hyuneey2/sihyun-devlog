# 반복 일정 처리를 위한 데이터베이스 설계 기록

일정 관리 기능을 설계하며 반복 일정(Recurring Schedule)의 그룹화 방식을 고민했다.

초기에는 반복 일정 중 첫 번째로 생성되는 일정의 `scheduleId`를 해당 그룹의 `groupId`로 사용하는 방식을 고려했다. 별도의 테이블 생성 없이 일정들을 하나로 묶을 수 있어 구조가 단순해 보였기 때문이다. 하지만 데이터의 수정과 삭제 범위를 구체화하는 과정에서 설계의 한계가 드러났다.

---

## 첫 번째 일정 ID 종속성의 한계

반복 일정은 특정 회차(단건)만 수정하거나, 전체 일정을 일괄 수정할 수 있어야 한다. 만약 그룹의 기준이 되는 첫 번째 일정이 삭제되면 다음과 같은 구조적 문제가 발생한다.

* **기준 상실:** 첫 일정이 삭제될 경우, 어떤 값을 새로운 `groupId`로 승계할지 모호해진다.
* **책임의 혼재:** 전체 수정 시 반복 조건(시작일, 종료일, 요일 등)을 어느 레코드에서 읽어와야 할지 기준이 불명확하다.
* **데이터 중복:** 개별 일정 로우(Row)마다 반복 조건을 중복해서 저장해야 한다.
* **로직 비대화:** 단일 일정과 반복 일정의 책임이 하나의 테이블에 섞여 비즈니스 로직이 복잡해진다.

이 문제는 단순히 컬럼 하나를 추가해서 해결될 일이 아니었다. 핵심은 **반복 규칙의 생명주기(Lifecycle)를 어디서 관리할 것인가**를 명확히 정하는 것이었다.

---

## 테이블 분리를 통한 책임 명확화

반복 규칙을 독립적으로 관리하기 위해 `schedule_repeat_group` 테이블을 별도로 분리했다.

| 테이블 | 책임 |
| --- | --- |
| `schedule` | 실제 날짜에 매핑된 개별 일정 및 완료 상태 관리 |
| `schedule_repeat_group` | 반복 유형, 시작 및 종료일, 반복 요일 등 규칙 관리 |

각 개별 일정(`schedule`)은 nullable한 `groupId`를 외래 키로 가진다. 단일 일정은 `groupId`가 `null`이며, 반복 일정은 생성된 그룹의 ID를 참조한다.

테이블을 분리하고 책임을 나누니 수정과 삭제 범위(Scope)에 대한 처리 규칙도 명확해졌다.

### 단건 처리 (SINGLE)

특정 회차의 일정만 수정할 경우, 해당 일정의 `groupId`를 `null`로 업데이트하여 그룹에서 분리한다. 이후부터 이 일정은 독립된 단일 일정으로 취급된다.

### 일괄 처리 (ALL)

반복 그룹 전체를 수정할 경우, 개별 일정이 아닌 `schedule_repeat_group`의 반복 조건을 갱신한다. 이후 변경된 조건에 맞추어 하위 `schedule` 레코드들을 재계산하여 갱신하거나 재생성한다.

---

## 존재하지 않는 예외 날짜 처리 정책

매월 31일이나 윤년의 2월 29일과 같이 특정 월이나 연도에 존재하지 않는 날짜에 대한 생성 정책도 확립해야 했다.

이 경우 날짜를 임의로 앞뒤로 당겨서 생성하지 않고, **해당 회차를 건너뛰는(Skip)** 정책을 채택했다. 시스템이 예외를 보정한다는 명목으로 임의의 날짜로 변경하면, 사용자가 의도하지 않은 날짜에 일정이 생성되는 부작용을 낳기 때문이다.

---

## 요약

초기에는 테이블을 추가하는 것이 시스템의 복잡도를 높인다고 생각했다. 하지만 데이터 구조의 진정한 단순함은 테이블의 개수가 아니라 **각 데이터의 책임이 얼마나 명확하게 분리되어 있는지**에 달렸음을 확인했다.

반복 그룹을 분리한 결과, API 응답 구조, 수정/삭제 범위 분기, 트랜잭션 처리까지 모두 일관된 기준으로 제어할 수 있었다. 코드를 구현하기 전 데이터의 생명주기와 비즈니스 정책을 명확히 정의하는 것이 이후 발생할 수 있는 수많은 예외 처리를 방지하는 핵심이다.
