TAB 학회에서 코딩테스트 준비 스터디를 하며 배열, 스택, 큐 같은 기본 자료구조부터 완전탐색과 그리디까지 다시 공부했다. 처음에는 정답 코드를 만드는 데 집중했지만, 풀이를 서로 설명하는 과정에서 더 중요한 질문이 생겼다.

> 왜 이 자료구조를 사용했고, 이 풀이는 제한 시간 안에 끝날 수 있는가?

같은 정답이라도 선택한 구조와 시간복잡도를 설명할 수 있어야 다른 문제에도 적용할 수 있었다.

## 자료구조는 문제 이름이 아니라 연산으로 고른다

자료구조를 외울 때는 특징보다 문제에서 자주 수행하는 연산을 기준으로 비교했다.

| 자료구조 | 빠른 연산 | 주의할 연산 |
| --- | --- | --- |
| 배열·리스트 | 인덱스로 접근 `O(1)` | 중간 삽입·삭제 `O(N)` |
| 연결 리스트 | 위치를 알고 있을 때 삽입·삭제 `O(1)` | 특정 위치 탐색 `O(N)` |
| 스택 | 뒤에서 삽입·삭제 `O(1)` | 중간 원소 접근에 부적합 |
| 큐 | `deque`의 양 끝 삽입·삭제 `O(1)` | 리스트의 `pop(0)`은 `O(N)` |
| 우선순위 큐 | 최솟값·최댓값 반복 조회 `O(log N)` | 임의 원소 탐색에는 부적합 |

백준 2164번 카드 문제에서는 맨 앞 카드를 버리고 다음 카드를 뒤로 보내는 연산을 반복한다. 일반 리스트에서 첫 원소를 지우면 남은 원소를 모두 당겨야 하지만, `deque.popleft()`는 앞에서 꺼내는 연산에 맞게 설계되어 있다. 문제의 핵심은 큐를 안다는 사실보다 **반복되는 연산에 맞는 구현을 고르는 것**이었다.

절댓값 힙 문제에서는 우선순위가 두 단계였다.

```python
heapq.heappush(heap, (abs(value), value))
```

파이썬의 튜플은 앞 원소부터 비교한다. 따라서 먼저 절댓값이 작은 수를 고르고, 절댓값이 같으면 실제 값이 작은 수를 고른다. 별도의 비교 함수를 만들지 않고도 문제의 정렬 기준을 자료구조에 그대로 표현할 수 있었다.

## 완전탐색은 느린 풀이가 아니라 제한을 확인한 풀이다

완전탐색은 가능한 경우를 모두 확인하므로 답을 놓치지 않는다. 대신 경우의 수가 커지면 실행 시간이 급격히 늘어난다. 그래서 코드를 작성하기 전에 입력 범위와 연산 횟수를 먼저 계산했다.

N개의 수에서 두 개를 고르는 경우는 다음과 같다.

```text
N × (N - 1) / 2
```

시간복잡도는 `O(N²)`이다. N이 1,000,000이라면 모든 쌍을 확인할 수 없고, 최댓값 두 개만 필요하다면 한 번 순회하는 `O(N)` 풀이가 적절하다.

반대로 일곱 난쟁이 문제는 9명 중 제외할 2명을 고르면 된다. 경우의 수는 `9C2 = 36`뿐이다. 전체 키의 합에서 두 명의 키를 뺐을 때 100이 되는지를 모두 확인해도 충분히 빠르다.

완전탐색을 사용할지 결정하는 순서는 단순했다.

1. 가능한 경우의 수를 계산한다.
2. 각 경우에서 수행할 연산 수를 곱한다.
3. 입력 최댓값에서도 감당할 수 있으면 가장 확실한 완전탐색을 사용한다.
4. 어렵다면 중복 계산을 줄이거나 다른 관점으로 문제를 바꾼다.

## 그리디는 가장 좋아 보이는 선택이 아니라 증명 가능한 선택이다

그리디는 매 순간 가장 유리한 선택을 한다. 하지만 지금 가장 커 보이는 값을 고른다고 항상 전체 정답이 되는 것은 아니다. 지역 최적 선택이 이후 선택을 방해하지 않고, 최종적으로 전체 최적해로 이어지는 이유를 설명할 수 있어야 한다.

숫자에서 K개의 자릿수를 지워 가장 큰 수를 만드는 문제는 앞자리의 영향이 더 크다는 점을 이용할 수 있다.

```python
stack = []

for digit in number:
    while stack and k > 0 and stack[-1] < digit:
        stack.pop()
        k -= 1
    stack.append(digit)

if k > 0:
    stack = stack[:-k]
```

현재 숫자보다 작은 앞자리 숫자를 제거하면 더 큰 숫자를 더 앞에 둘 수 있다. 앞자리가 큰 수가 항상 더 크기 때문에 이 선택은 뒤의 선택보다 우선한다. 끝까지 제거 횟수가 남았다면 이미 내림차순에 가까운 상태이므로 뒤에서 제거한다.

코드를 외우는 것보다 다음 두 질문이 중요했다.

- 지금 선택을 나중에 바꿀 필요가 없는가?
- 다른 최적해가 있더라도 현재 선택을 포함하는 최적해로 바꿀 수 있는가?

## 설명하는 과정이 풀이를 검증했다

스터디에서는 각자 문제를 직접 풀고, 사용한 자료구조와 풀이 방식을 설명했다. 같은 문제도 반복문으로 직접 구현한 풀이, 내장 자료구조를 활용한 풀이, 시간복잡도를 줄인 풀이가 달랐다.

설명하다 막히는 부분은 대부분 코드가 아니라 판단의 근거였다. 이후에는 정답을 맞힌 뒤에도 입력 범위, 자료구조, 시간복잡도, 예외 입력을 한 번 더 확인하게 됐다. 코딩테스트 준비를 통해 얻은 가장 큰 변화는 알고리즘 이름을 많이 외운 것이 아니라, **문제를 풀기 전에 선택 기준부터 세우는 습관**이었다.
