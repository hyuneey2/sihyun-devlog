2025년 React 스터디를 시작했을 때는 컴포넌트를 만들고 화면에 렌더링하는 것 자체가 목표였다. 하지만 페이지 수가 늘고 API를 연결하면서 중요한 것은 개별 화면보다 **화면 사이의 구조와 데이터 흐름**이라는 것을 알게 됐다.

## 라우팅은 컴포넌트를 바꾸는 것 이상이었다

전통적인 페이지 이동은 새로운 URL에 해당하는 HTML을 서버에 다시 요청한다. React Router를 사용하는 SPA에서는 문서 전체를 새로 받지 않고, 현재 애플리케이션 안에서 경로에 맞는 컴포넌트를 렌더링한다.

```tsx
const router = createBrowserRouter([
  {
    path: "/",
    element: <RootLayout />,
    errorElement: <NotFoundPage />,
    children: [
      { index: true, element: <HomePage /> },
      { path: "posts", element: <PostsPage /> },
      { path: "posts/:postId", element: <PostDetailPage /> },
    ],
  },
]);
```

여기서 `RootLayout`은 헤더와 공통 레이아웃을 맡고, 자식 경로의 화면은 `Outlet`에 표시된다. 페이지마다 헤더 코드를 복사하지 않아도 되고, 공통 UI와 개별 페이지의 책임도 분명해진다.

`Link`를 사용하면 문서 전체를 새로고침하지 않고 경로만 바꿀 수 있다. `errorElement`나 별도 404 페이지를 구성하면 존재하지 않는 경로도 서비스의 UX 안에서 처리할 수 있다.

라우팅을 공부하며 얻은 기준은 세 가지였다.

- URL만 보고도 어떤 화면인지 이해할 수 있어야 한다.
- 공통 레이아웃과 페이지별 내용을 분리한다.
- 정상 경로뿐 아니라 잘못된 경로의 흐름도 설계한다.

## 컴포넌트는 작게 나누는 것이 아니라 책임으로 나눈다

처음에는 파일이 짧을수록 좋은 컴포넌트라고 생각했다. 실제로는 너무 잘게 나누면 데이터가 여러 단계를 거쳐 전달되고, 반대로 한 파일에 모두 넣으면 수정 범위를 파악하기 어렵다.

다음 기준으로 분리하는 편이 더 명확했다.

- 여러 페이지에서 같은 형태와 동작으로 재사용되는가?
- 하나의 독립된 사용자 행동을 담당하는가?
- 데이터 요청과 화면 표현을 따로 테스트하거나 변경할 가능성이 있는가?
- 이름을 붙였을 때 책임을 한 문장으로 설명할 수 있는가?

헤더, 버튼, 입력창처럼 반복되는 UI는 공통 컴포넌트로 분리하고, 페이지는 필요한 데이터를 조합하는 역할을 맡겼다. 이후 프로젝트에서도 `components`, `pages`, `api`, `contexts`처럼 역할을 기준으로 폴더를 나누는 출발점이 됐다.

## API 통신은 요청 한 번으로 끝나지 않는다

스터디에서는 Fetch API와 Axios의 차이를 비교하고, 실제 응답을 화면에 반영했다.

| 항목 | Fetch API | Axios |
| --- | --- | --- |
| 설치 | 브라우저 내장 | 별도 패키지 |
| JSON 변환 | `response.json()` 호출 | 응답 데이터 자동 변환 |
| 4xx·5xx 처리 | `response.ok` 직접 확인 | 기본적으로 오류로 처리 |
| 공통 요청 처리 | 직접 함수 구성 | 인터셉터 제공 |
| 실행 환경 | 주로 브라우저 | 브라우저와 Node.js |

어느 도구가 항상 더 좋은 것은 아니었다. 요청 수가 적고 별도 기능이 필요 없다면 Fetch로 충분하다. 인증 토큰, 공통 오류 처리, 타임아웃처럼 모든 요청에 같은 규칙이 필요하다면 Axios 인스턴스와 인터셉터가 편리하다.

더 중요한 것은 도구보다 요청의 상태를 구분하는 일이었다.

```text
idle → loading → success
              ↘ error
```

- 요청 전에는 불필요한 호출을 막을 조건이 필요하다.
- 요청 중에는 중복 제출을 막고 로딩 상태를 보여 준다.
- 성공하면 받은 데이터로 화면을 갱신한다.
- 결과가 비어 있으면 실패와 다른 안내를 보여 준다.
- 실패하면 사용자가 다음 행동을 결정할 수 있는 메시지를 제공한다.

## `useEffect`는 실행 시점보다 정리 시점까지 봐야 했다

이벤트 리스너나 타이머를 Effect에서 등록하면 컴포넌트가 사라지거나 의존성이 바뀔 때 기존 작업을 정리해야 한다.

```tsx
useEffect(() => {
  const handleResize = () => setIsMobile(window.innerWidth < 768);

  window.addEventListener("resize", handleResize);
  handleResize();

  return () => {
    window.removeEventListener("resize", handleResize);
  };
}, []);
```

정리 함수가 없으면 다시 렌더링되는 과정에서 이벤트가 중복 등록되거나, 화면에서 사라진 컴포넌트의 작업이 계속 남을 수 있다. Effect를 “렌더링 후 실행하는 코드”가 아니라 외부 시스템과 연결하고 해제하는 과정으로 이해하게 됐다.

## 스터디 내용은 실제 프로젝트에서 기준이 됐다

React Router로 배운 공통 레이아웃과 중첩 경로는 여러 페이지를 가진 프로젝트의 뼈대가 됐다. API 통신에서 구분한 로딩·성공·빈 결과·실패 상태는 로그인, 참가 신청, 목록 조회 화면을 구현할 때 그대로 사용했다.

React 스터디에서 가장 오래 남은 것은 특정 훅의 사용법이 아니었다. URL, 컴포넌트, 상태, API가 각각 어떤 책임을 가져야 하는지 생각하는 습관이었다. 화면이 동작하는 데서 끝내지 않고, 기능이 늘어도 수정할 위치를 찾을 수 있는 구조를 만드는 출발점이 됐다.
