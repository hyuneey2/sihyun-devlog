프론트엔드 프로젝트를 먼저 경험한 뒤 UMC 10기 Node.js 파트에서 서버 공부를 시작했다. 화면에서는 API 함수를 호출하면 데이터가 돌아왔지만, 서버 안에서 요청이 어떤 과정을 거쳐 처리되는지는 정확히 설명하기 어려웠다.

주차별 학습과 과제를 진행하며 서버, 데이터베이스, API, 인증을 따로 외우는 대신 하나의 요청 흐름으로 연결해 보았다. 과제를 꾸준히 수행해 Best Workbook으로 선정됐지만, 더 의미 있었던 변화는 동작하는 코드를 따라 쓰는 단계에서 각 계층의 책임을 설명하는 단계로 넘어간 것이었다.

## 브라우저의 요청이 서버에 도착하기까지

처음에는 서버 코드를 작성하기 전에 URL을 입력한 뒤 화면이 나타나는 과정을 정리했다.

```text
도메인 입력
→ DNS가 IP 주소 확인
→ IP와 PORT를 이용해 서버와 연결
→ HTTP 요청 전송
→ 서버가 요청 처리
→ HTTP 응답 반환
→ 브라우저가 화면 렌더링
```

IP는 네트워크에서 통신할 장치를 찾는 주소이고, PORT는 한 장치 안에서 요청을 받을 프로세스를 구분한다. TCP는 연결과 데이터 순서를 보장하고, HTTP는 그 연결 위에서 요청과 응답의 형식을 정한다.

Web Server와 WAS의 차이도 이 흐름 안에서 이해했다. Web Server는 HTML, CSS, 이미지 같은 정적 자원을 전달하는 데 적합하다. WAS는 요청에 따라 로직을 실행하고 데이터베이스를 조회해 동적인 응답을 만든다. Node.js 애플리케이션에서 작성한 API 서버는 후자의 역할에 가깝다.

## API URL은 동작이 아니라 자원을 표현한다

REST API를 설계할 때 처음에는 URL에 동사를 넣고 싶었다.

```text
POST /createPost
GET /getPostList
```

하지만 HTTP 메서드가 이미 행위를 나타내므로 URL은 다루는 자원을 중심으로 표현하는 편이 일관적이었다.

```text
POST   /posts
GET    /posts
GET    /posts/:postId
PATCH  /posts/:postId
DELETE /posts/:postId
```

이 구조에서는 같은 자원에 대한 생성, 조회, 수정, 삭제가 한눈에 보인다. 상태 코드도 단순 성공과 실패로만 나누지 않고 상황에 맞게 구분했다.

- `200 OK`: 조회·수정 성공
- `201 Created`: 생성 성공
- `400 Bad Request`: 입력값이나 요청 형식 오류
- `401 Unauthorized`: 인증 정보 없음 또는 유효하지 않음
- `404 Not Found`: 요청한 자원을 찾을 수 없음
- `500 Internal Server Error`: 서버 내부 처리 실패

프론트엔드가 오류 상황을 구분하려면 상태 코드뿐 아니라 일관된 응답 구조와 애플리케이션 에러 코드도 필요하다는 점을 이후 협업에서 더 분명히 체감했다.

## 데이터베이스 설계가 API의 기준이 됐다

API를 먼저 만들고 필요한 값을 그때그때 저장하면 데이터 관계가 쉽게 꼬인다. ERD를 그리며 엔티티, 속성, 기본 키와 외래 키를 먼저 정리했다.

예를 들어 사용자와 게시글 관계는 다음처럼 표현할 수 있다.

```text
User 1 ─── N Post
```

한 사용자는 여러 게시글을 작성할 수 있고, 각 게시글은 작성자 한 명을 참조한다. 이 관계가 정해지면 게시글 생성 요청에 왜 사용자 식별값이 필요한지, 사용자 삭제 시 게시글을 어떻게 처리할지, 작성자별 게시글을 어떤 조건으로 조회할지가 이어진다.

SQL을 공부할 때도 단순 문법보다 API가 요구하는 결과를 만드는 데 집중했다.

- 조건에 맞는 데이터는 `WHERE`
- 여러 테이블의 관계는 `JOIN`
- 집계 결과는 `GROUP BY`
- 중복이나 존재 여부 확인은 서브쿼리 또는 조인
- 많은 결과를 나누어 주기 위한 페이지네이션

데이터 구조와 조회 조건을 먼저 이해하면 서비스 코드에서 불필요한 반복이나 여러 번의 조회를 줄일 수 있었다.

## 계층을 나눈 이유는 파일을 정리하기 위해서가 아니었다

Node.js 프로젝트에서는 요청 처리를 역할별로 나눴다.

```text
Route
→ Controller
→ Service
→ Repository
→ Database
```

| 계층 | 책임 |
| --- | --- |
| Route | URL과 HTTP 메서드를 연결 |
| Controller | 요청값을 받고 응답 형식을 결정 |
| Service | 서비스 규칙과 처리 순서를 담당 |
| Repository | 데이터베이스 조회·저장을 담당 |

회원가입을 예로 들면 Controller는 입력값을 전달받고, Service는 중복 이메일 확인과 비밀번호 해시 같은 규칙을 처리하며, Repository는 실제 사용자 데이터를 저장한다.

모든 로직을 Controller에 넣어도 작은 기능은 동작한다. 하지만 데이터베이스가 바뀌거나 규칙이 추가되면 요청 처리, 비즈니스 로직, 쿼리를 함께 수정해야 한다. 계층 분리는 파일 수를 늘리는 형식이 아니라 **변경 이유가 다른 코드를 분리하는 방법**이었다.

## 인증은 로그인 성공 이후의 요청까지 포함한다

비밀번호는 원문으로 저장하지 않고 `bcrypt`로 해시한 값을 저장했다. 로그인할 때 입력한 비밀번호와 저장된 해시를 비교하고, 인증에 성공하면 JWT를 발급한다.

```text
회원가입: 비밀번호 입력 → 해시 생성 → DB 저장
로그인: 비밀번호 입력 → 해시 비교 → JWT 발급
인증 요청: Authorization 헤더 → 토큰 검증 → 사용자 식별
```

JWT는 로그인 여부를 표시하는 문자열이 아니라, 이후 요청에서 사용자를 식별하기 위한 서명된 정보다. 따라서 발급뿐 아니라 만료 시간, 서명 키 관리, 잘못된 토큰 처리, 인증 미들웨어의 책임까지 함께 봐야 했다.

또한 인증과 인가를 구분했다. 인증은 사용자가 누구인지 확인하는 과정이고, 인가는 확인된 사용자가 해당 기능을 사용할 권한이 있는지 판단하는 과정이다.

## 백엔드를 배우며 프론트엔드도 다르게 보였다

Node.js 스터디 이후 API 응답을 볼 때 단순히 필요한 필드가 있는지만 확인하지 않게 됐다. 데이터 관계와 조회 비용, 입력 검증, 인증 흐름, 오류가 발생한 계층까지 함께 생각하게 됐다.

이 경험은 이후 NestJS와 TypeORM으로 일정 API를 설계할 때 이어졌다. 프레임워크는 달라졌지만 모듈의 책임을 나누고, 엔티티 관계를 먼저 정하고, 요청·응답과 예외를 일관되게 관리한다는 기준은 같았다.

서버 공부를 통해 얻은 가장 큰 변화는 프론트엔드와 백엔드를 별개의 영역으로 보지 않게 된 것이다. 사용자의 한 번의 행동이 화면에서 시작해 네트워크, 서버 로직, 데이터베이스를 거쳐 다시 화면으로 돌아오는 전체 흐름을 기준으로 기능을 보게 됐다.
