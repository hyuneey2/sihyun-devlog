## 프론트엔드에서 조합하던 데이터를 전용 API로 분리한 이유

> 내 댓글과 게시글 썸네일을 조회하기 위해 반복되던 요청을 줄이고, 화면에 필요한 데이터를 한 번의 요청으로 받을 수 있도록 API 구조를 조정한 기록입니다.

기능을 구현할 때는 기존 API를 조합해서 처리할 수 있는지 먼저 확인했습니다. 새로운 API를 만들지 않아도 프론트엔드에서 필요한 데이터를 만들 수 있다면 그대로 사용하는 편이 단순하다고 생각했습니다.

하지만 구현 가능 여부와 사용자 경험은 별개의 문제였습니다. 기존 API만으로 화면을 완성할 수 있어도 요청 수가 많아지고 로딩 시간이 길어진다면 조회 구조를 다시 검토해야 했습니다.

이 기준으로 내 댓글 조회와 게시글 썸네일 조회 구조를 변경했습니다.

## 기존 API만으로 내 댓글을 조회한 방법

마이페이지에는 로그인한 사용자가 작성한 댓글을 모아서 보여주는 화면이 필요했습니다.

당시에는 게시글별 댓글 조회 API만 있었습니다.

```text
GET /posts/{postId}/comments
```

현재 사용자가 작성한 댓글을 한 번에 조회하는 API는 없었습니다. 기존 API만 이용하려면 먼저 모든 게시글을 가져온 뒤, 각 게시글의 댓글을 조회해야 했습니다.

```text
전체 게시글 조회
→ 게시글마다 댓글 목록 조회
→ 작성자 확인
→ 현재 사용자의 댓글만 필터링
```

게시글이 `N`개라면 요청 수도 함께 증가했습니다.

```text
게시글 목록 조회 1회
+ 게시글별 댓글 조회 N회
= 총 N + 1회
```

DB에서 말하는 N+1 쿼리 문제와 같은 개념은 아니지만, 프론트엔드에서 N+1 형태의 API 요청이 발생하는 구조였습니다.

## 기능은 동작했지만 사용하기 어려웠다

처음에는 기존 API로 기능을 구현했습니다. 게시글 수가 적을 때는 사용할 수 있었지만 데이터가 늘어나면서 로딩 시간이 길어졌습니다.

작성한 댓글이 많거나 조회할 게시글이 많을 때는 화면이 표시되기까지 30초 가까이 걸리기도 했습니다.

기능 자체는 동작했지만 사용자가 결과를 기다려야 했습니다. 댓글이 없는 것인지 아직 불러오는 중인지 구분하기도 어려웠습니다.

프론트엔드에서 병렬 요청을 보내거나 로딩 UI를 추가할 수도 있습니다. 하지만 요청해야 하는 데이터의 양과 횟수는 줄어들지 않습니다.

```text
순차 요청을 병렬 요청으로 변경
→ 일부 대기 시간 감소 가능
→ 게시글 수만큼 요청하는 구조는 유지

로딩 화면 추가
→ 대기 상태 안내 가능
→ 실제 응답 시간은 그대로
```

화면 처리만으로 해결하기보다 현재 사용자 기준으로 댓글을 조회하는 API가 필요하다고 판단했습니다.

## 내 댓글 조회 API 추가

로그인한 사용자의 댓글을 한 번에 받을 수 있도록 전용 API를 추가했습니다.

```text
내 댓글 조회 1회
→ 현재 사용자가 작성한 댓글 목록 반환
```

기존 구조에서는 프론트엔드가 모든 게시글과 댓글을 받은 뒤 사용자를 기준으로 필터링했습니다. 변경 후에는 서버가 인증 정보로 현재 사용자를 확인하고 해당 사용자의 댓글만 조회합니다.

```text
변경 전

전체 게시글 조회
→ 게시글별 댓글 조회
→ 프론트엔드에서 사용자별 필터링
```

```text
변경 후

내 댓글 조회
→ 서버에서 사용자별 조회
→ 필요한 댓글만 반환
```

요청 수가 데이터 개수에 따라 늘어나지 않고 한 번으로 고정됐습니다. 프론트엔드에서도 여러 요청의 성공 여부와 로딩 상태를 따로 관리할 필요가 없어졌습니다.

## 게시글 썸네일에서도 같은 문제가 발생했다

메인 페이지에는 최근 예배 게시글 세 개를 카드 형태로 보여주는 영역이 있었습니다. 각 카드에는 게시글 제목과 썸네일이 필요했습니다.

게시글 목록 API에는 썸네일 정보가 없었고, 유튜브 링크와 업로드 이미지는 상세 게시글의 `content`에서만 확인할 수 있었습니다.

프론트엔드에서 썸네일을 만들려면 다음 과정이 필요했습니다.

```text
게시글 목록 조회
→ 노출할 게시글 선택
→ 각 게시글 상세 조회
→ content에서 유튜브 링크 또는 이미지 확인
→ 썸네일 결정
```

메인 페이지에서 세 개만 보여줘도 최소 네 번의 요청이 발생합니다.

```text
게시글 목록 조회 1회
+ 게시글 상세 조회 3회
= 총 4회
```

게시글 수가 제한되어 있어 내 댓글 조회만큼 큰 지연이 생기지는 않았습니다. 하지만 목록에 보여줄 값을 얻기 위해 상세 API를 반복 호출한다는 구조는 같았습니다.

## 프론트엔드에서 썸네일을 만들지 않은 이유

유튜브 링크가 있다면 영상 ID를 추출해 썸네일 주소를 만들 수 있습니다.

```text
https://www.youtube.com/watch?v={videoId}
```

```text
https://img.youtube.com/vi/{videoId}/hqdefault.jpg
```

따라서 프론트엔드에서 처리하는 것도 가능합니다. 그러나 썸네일을 만들려면 먼저 각 게시글의 상세 내용을 가져와야 했습니다.

문제는 썸네일 URL을 만드는 코드가 아니라, 썸네일을 만들기 위한 원본 정보가 목록 응답에 없다는 점이었습니다.

목록 화면에서 계속 필요한 값이라면 목록 API가 해당 값을 제공하는 편이 적절하다고 판단했습니다. 프론트엔드가 상세 데이터를 반복해서 조회하고 같은 규칙을 적용할 이유가 없었습니다.

## 목록 API에 `thumbnailUrl` 추가

게시글 목록 응답에 `thumbnailUrl`을 추가했습니다.

썸네일을 결정하는 기준은 다음과 같이 정했습니다.

```text
유튜브 링크가 있음
→ 유튜브 썸네일 URL 반환

유튜브 링크는 없고 업로드 이미지가 있음
→ 업로드 이미지 URL 반환

둘 다 없음
→ null 반환
```

응답 예시는 다음과 같습니다.

```json
{
  "postId": 1,
  "title": "주일 예배",
  "thumbnailUrl": "https://img.youtube.com/vi/videoId/hqdefault.jpg"
}
```

둘 다 없는 경우에는 `null`을 받고 프론트엔드에서 기본 이미지를 표시했습니다.

```ts
const thumbnailSrc = post.thumbnailUrl ?? DEFAULT_THUMBNAIL;
```

서버는 게시글 데이터에 따라 썸네일 값을 결정하고, 프론트엔드는 받은 값을 화면에 표시하는 역할만 담당합니다.

## 두 문제의 해결 방식이 달랐던 이유

내 댓글과 게시글 썸네일은 모두 반복 요청이 발생한 문제였지만 해결 방식은 달랐습니다.

내 댓글은 현재 사용자를 기준으로 별도의 데이터 집합을 조회해야 했습니다. 기존 게시글별 댓글 API의 응답에 값을 추가하는 것만으로는 해결하기 어려웠습니다. 따라서 전용 조회 API를 추가했습니다.

```text
내 댓글
→ 사용자 기준의 새로운 조회 조건
→ 전용 API 추가
```

썸네일은 새로운 데이터 목록이 아니라 게시글 목록에 함께 표시할 값이었습니다. 별도의 썸네일 API를 추가하면 다시 요청이 늘어납니다. 따라서 기존 목록 응답에 필요한 필드만 추가했습니다.

```text
게시글 썸네일
→ 기존 목록 항목에 필요한 파생 값
→ 목록 응답 필드 추가
```

새로운 화면이 생길 때마다 API를 만드는 것이 아니라, 필요한 데이터의 성격에 따라 해결 방법을 나눴습니다.

## API가 필요한지 판단한 기준

프론트엔드에서 데이터를 조합할 수 있다는 이유만으로 기존 구조를 유지하지 않았습니다. 다음 기준으로 API 변경이 필요한지 판단했습니다.

### 요청 수가 데이터에 따라 증가하는가

게시글 수가 늘어날 때 댓글이나 상세 조회 요청도 함께 증가한다면 화면의 응답 시간도 데이터 양에 영향을 받습니다.

```text
데이터 증가
→ 요청 증가
→ 실패 가능성 증가
→ 로딩 시간 증가
```

### 화면 하나를 위해 여러 API를 반복 호출하는가

목록 화면을 구성하기 위해 각 항목의 상세 API를 다시 호출한다면 목록 응답에 필요한 값이 빠져 있는지 확인할 필요가 있습니다.

### 서버가 더 직접적으로 조회할 수 있는가

서버는 현재 사용자와 데이터의 관계를 알고 있습니다. 전체 데이터를 프론트엔드에 전달한 뒤 다시 필터링하는 것보다 서버에서 조건에 맞는 데이터만 조회하는 편이 효율적입니다.

### 같은 조합 로직을 다른 화면에서도 사용할 가능성이 있는가

유튜브 링크를 분석하거나 현재 사용자의 데이터를 찾는 로직이 여러 화면에 반복되면 화면마다 결과가 달라질 수 있습니다. 공통 규칙은 서버에서 관리하는 편이 일관성을 유지하기 쉽습니다.

### 응답에 불필요한 데이터가 포함되지는 않는가

반복 요청을 줄이기 위해 상세 응답 전체를 목록에 포함하면 목록 API가 무거워질 수 있습니다. 화면에 필요한 최소한의 값만 추가해야 합니다.

썸네일의 경우 `content` 전체가 아니라 `thumbnailUrl` 하나만 목록 응답에 추가했습니다.

## 사용자 경험을 기준으로 구조를 바꿨다

처음에는 새로운 API를 요청하지 않고 기존 API만으로 구현하는 것이 효율적이라고 생각했습니다. 실제로 기능도 완성할 수 있었습니다.

하지만 사용자에게는 프론트엔드와 백엔드가 어떤 방식으로 데이터를 조합하는지 보이지 않습니다. 화면이 늦게 뜨면 서비스가 느린 것으로 느낍니다.

내 댓글 화면에서 30초 가까이 기다려야 하는 구조를 로딩 UI로 감추는 것은 해결이 아니었습니다. 메인 화면의 썸네일을 위해 상세 요청을 반복하는 것도 데이터가 늘어났을 때 같은 문제가 될 수 있었습니다.

API 개수를 줄이는 것보다 사용자가 필요한 화면을 적은 요청으로 받을 수 있도록 만드는 것이 중요했습니다.

## 정리

기존 API만으로 내 댓글과 게시글 썸네일을 구현할 수 있었습니다. 다만 프론트엔드에서 전체 목록을 조회하고 항목마다 추가 요청을 보내야 했습니다.

내 댓글 조회는 게시글 수에 따라 요청이 증가했고 실제 로딩 시간도 길어졌습니다. 현재 사용자의 댓글을 한 번에 조회하는 API를 추가해 한 번의 요청으로 처리했습니다.

게시글 썸네일은 목록을 받은 뒤 각 게시글의 상세 내용을 다시 조회해야 했습니다. 목록 API에 `thumbnailUrl`을 추가하고 유튜브 링크, 업로드 이미지, 기본 이미지 순서로 처리했습니다.

두 사례를 통해 API 필요 여부를 기능 구현 가능성만으로 판단해서는 안 된다는 점을 확인했습니다. 기존 API를 조합해 구현할 수 있어도 요청 수와 로딩 시간이 사용자 경험을 해친다면 조회 구조를 바꿀 필요가 있습니다.
