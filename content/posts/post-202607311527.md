## 쿠키 기반 로그인 연동 중 CORS 오류를 해결한 과정

프론트엔드와 백엔드의 로그인 API를 연동했을 때 발생한 CORS 오류를 해결한 기록입니다.

백엔드에서는 기존에 프론트엔드와 같은 도메인에서 개발해 별도의 CORS 설정을 사용하지 않았습니다. 프론트엔드는 CORS 오류를 접한 경험은 있었지만, Spring과 Nginx 설정까지는 알지 못했습니다.

오류 메시지와 응답 헤더를 확인하면서 원인을 하나씩 좁혀 갔습니다.

## 개발 환경

프론트엔드는 로컬과 Vercel 배포 환경에서 백엔드 API를 호출합니다.

```text
로컬 프론트엔드
http://localhost:5173

배포 프론트엔드
https://with-church-fe.vercel.app

백엔드 API
https://withchurch.site
```

로그인 인증에는 쿠키를 사용했습니다. Axios 요청에는 `withCredentials` 옵션이 설정되어 있었습니다.

```ts
axios.post('/api/auth/login', loginData, {
  withCredentials: true,
});
```

프론트엔드와 백엔드의 Origin이 다르기 때문에 브라우저의 CORS 정책이 적용되는 구조입니다.

## 첫 번째 오류: Credential 요청에서 와일드카드 사용

로그인 요청을 보내자 다음 오류가 발생했습니다.

```text
Response to preflight request doesn't pass access control check:

The value of the 'Access-Control-Allow-Origin' header in the response
must not be the wildcard '*' when the request's credentials mode is 'include'.
```

서버 응답에는 다음 헤더가 포함되어 있었습니다.

```http
Access-Control-Allow-Origin: *
```

일반적인 CORS 요청에서는 모든 Origin을 뜻하는 `*`를 사용할 수 있습니다. 하지만 쿠키를 포함한 Credential 요청에서는 사용할 수 없습니다.

프론트엔드에서 `withCredentials: true`를 사용한다면 서버도 다음 조건을 충족해야 합니다.

```http
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Credentials: true
```

`Access-Control-Allow-Origin`에는 `*`가 아닌 구체적인 Origin이 들어가야 합니다.

쿠키가 포함된 요청을 모든 출처에 허용하면 다른 사이트에서도 사용자의 인증 정보를 이용해 요청할 수 있습니다. 브라우저는 이를 막기 위해 Credential 요청과 와일드카드 Origin의 조합을 허용하지 않습니다.

## CORS 설정을 변경했지만 `*`가 계속 반환된 문제

서버 설정에서 허용 Origin을 변경했지만 브라우저에서는 계속 `*`가 반환됐습니다.

```http
Access-Control-Allow-Origin: *
```

코드는 수정됐지만 실행 중인 서버에는 변경 내용이 반영되지 않은 상태였습니다.

백엔드는 Docker 컨테이너로 실행되고 있었습니다. 기존 이미지로 생성된 컨테이너가 이전 설정을 사용하고 있을 가능성을 확인했습니다.

Docker 이미지를 다시 빌드하고 컨테이너를 재실행한 뒤 응답 헤더가 바뀌기 시작했습니다.

```text
설정 파일 수정
→ Docker 이미지 리빌드
→ 기존 컨테이너 재실행
→ 변경된 설정 반영
```

배포 환경에서는 코드를 수정하는 것과 실행 중인 애플리케이션에 변경 사항이 적용되는 것이 별개의 과정임을 확인했습니다.

## 두 번째 오류: 하나의 헤더에 Origin이 두 개 포함된 문제

Docker 리빌드 후 기존 오류는 사라졌지만 새로운 오류가 발생했습니다.

```text
The 'Access-Control-Allow-Origin' header contains multiple values
'https://with-church-fe.vercel.app, http://localhost:5173',
but only one is allowed.
```

로컬 환경과 배포 환경을 모두 허용하기 위해 두 주소를 하나의 응답 헤더에 넣은 것이 원인이었습니다.

```http
Access-Control-Allow-Origin: https://with-church-fe.vercel.app, http://localhost:5173
```

`Access-Control-Allow-Origin` 응답 헤더에는 하나의 Origin만 들어갈 수 있습니다.

서버의 허용 목록에는 여러 Origin을 등록할 수 있습니다.

```text
http://localhost:5173
https://with-church-fe.vercel.app
```

하지만 실제 응답에는 요청을 보낸 Origin 하나만 반환해야 합니다.

로컬 프론트엔드에서 요청했다면 다음과 같이 응답해야 합니다.

```http
Access-Control-Allow-Origin: http://localhost:5173
```

배포된 프론트엔드에서 요청했다면 다음과 같이 응답해야 합니다.

```http
Access-Control-Allow-Origin: https://with-church-fe.vercel.app
```

허용 Origin 목록과 `Access-Control-Allow-Origin` 응답 헤더는 구분해야 합니다.

## Preflight 요청 확인

로그인 요청 전에는 브라우저가 `OPTIONS` 메서드로 Preflight 요청을 보냅니다.

```text
OPTIONS /api/auth/login
```

브라우저는 실제 로그인 요청을 보내기 전에 서버가 현재 Origin과 요청 방식을 허용하는지 확인합니다.

Preflight 응답에는 다음과 같은 헤더가 필요합니다.

```http
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: POST, OPTIONS
Access-Control-Allow-Headers: Content-Type
```

Preflight 요청이 실패하면 실제 `POST /api/auth/login` 요청은 서버로 전송되지 않습니다.

오류가 로그인 API에서 발생한 것처럼 보여도 실제로는 그 전에 실행된 `OPTIONS` 요청이 차단된 상태일 수 있습니다.

## Nginx와 Spring의 CORS 설정 중복 확인

백엔드 서버 앞에는 Nginx가 있었습니다.

CORS 헤더를 Spring과 Nginx에서 모두 설정하면 응답 헤더가 중복될 수 있습니다.

Spring에서 다음 헤더를 반환하고,

```http
Access-Control-Allow-Origin: http://localhost:5173
```

Nginx에서도 별도의 헤더를 추가하면 브라우저에는 두 값이 전달될 수 있습니다.

```http
Access-Control-Allow-Origin: https://with-church-fe.vercel.app
```

브라우저는 이를 다음과 같이 해석할 수 있습니다.

```text
Access-Control-Allow-Origin:
http://localhost:5173, https://with-church-fe.vercel.app
```

하나의 응답에 여러 Origin이 포함되기 때문에 요청이 차단됩니다.

CORS 설정은 Spring 또는 Nginx 중 한 곳에서 관리하는 편이 안전합니다. 두 계층에서 설정한다면 같은 헤더가 중복되지 않는지 확인해야 합니다.

## 해결 방법

다음 기준으로 CORS 설정을 정리했습니다.

```text
1. Access-Control-Allow-Origin에서 * 제거
2. 로컬과 배포 프론트엔드 주소를 허용 목록에 등록
3. 요청 Origin과 일치하는 값 하나만 응답
4. Access-Control-Allow-Credentials를 true로 설정
5. OPTIONS 요청 허용
6. Spring과 Nginx의 CORS 헤더 중복 여부 확인
7. Docker 이미지 리빌드 및 컨테이너 재실행
```

허용할 Origin은 다음 두 주소입니다.

```text
http://localhost:5173
https://with-church-fe.vercel.app
```

요청을 보낸 Origin이 허용 목록에 포함되어 있다면 해당 값만 `Access-Control-Allow-Origin`으로 반환하도록 설정했습니다.

## 확인 방법

브라우저 개발자 도구의 Network 탭에서 `OPTIONS` 요청을 확인했습니다.

확인한 항목은 다음과 같습니다.

```text
Request Method
OPTIONS

Origin
http://localhost:5173

Access-Control-Allow-Origin
http://localhost:5173

Access-Control-Allow-Credentials
true
```

서버 설정 파일만 확인하는 것보다 실제 응답 헤더를 확인하는 것이 중요합니다.

설정 코드가 올바르더라도 Docker 컨테이너가 이전 이미지를 사용하거나 Nginx가 헤더를 추가하면 브라우저가 받는 결과는 달라질 수 있습니다.

## 정리

이번 문제에는 여러 원인이 함께 있었습니다.

처음에는 Credential 요청에 `Access-Control-Allow-Origin: *`가 사용되고 있었습니다. 설정을 수정한 뒤에는 Docker 컨테이너에 변경 사항이 반영되지 않았습니다. 리빌드 후에는 두 개의 Origin이 하나의 응답 헤더에 포함되는 문제가 발생했습니다.

오류 메시지에 따라 응답 상태를 나누어 확인했습니다.

```text
와일드카드 오류
→ 쿠키 요청에서 * 사용 여부 확인

설정 변경 후에도 같은 오류 발생
→ 실행 중인 Docker 컨테이너의 설정 반영 여부 확인

여러 Origin이 포함됐다는 오류
→ 응답 헤더 중복과 CORS 설정 위치 확인
```

CORS 오류는 프론트엔드 콘솔에 나타나지만 해결에 필요한 정보는 서버의 응답 헤더에 있습니다.

Credential 요청에서는 다음 조건이 함께 맞아야 합니다.

```text
프론트엔드
withCredentials: true

서버
구체적인 Access-Control-Allow-Origin
Access-Control-Allow-Credentials: true
```

또한 허용 목록에는 여러 Origin을 등록할 수 있지만, 실제 응답 헤더에는 요청을 보낸 Origin 하나만 포함해야 합니다.

이번 연동을 통해 CORS 정책뿐 아니라 Nginx, Docker, Preflight 요청이 로그인 API 호출에 어떤 영향을 주는지 확인했습니다.
