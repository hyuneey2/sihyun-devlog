# 한국외국어대학교 독서마라톤 프론트엔드 단독 개발 기록

한국외국어대학교 글로벌캠퍼스 도서관에서 주관하는 독서마라톤 웹서비스의 프론트엔드를 단독으로 개발했다. 기존에 여러 도구로 파편화되어 있던 참가 신청, 독서일지 제출, 관리자 검토, 현황 집계 과정을 하나의 웹서비스로 통합하는 프로젝트다.

실제 사용자가 이용하고 다음 기수에도 운영되어야 하는 서비스이므로, 단순한 화면 구현을 넘어 유지보수와 확장성을 고려한 아키텍처 설계가 필요했다. 기술 스택 선정 이유와 개발 과정에서 겪은 트러블슈팅을 중심으로 정리했다.

---

## 1. 기술 스택 선정 기준

단독 개발인 만큼 생산성과 안정성을 모두 확보해야 했다.

* **React**: 사용자와 관리자 화면에서 중복되는 UI(테이블, 폼, 모달 등)를 컴포넌트로 분리하여 재사용하기 위해 선택했다.
* **TypeScript**: 독서 거리 환산, 완주율 계산 등 비즈니스 로직이 많고, API 명세가 확정되지 않은 상태에서 데이터 구조를 안전하게 모킹(Mocking)하기 위해 정적 타입 시스템이 필수적이었다.
* **Vite**: Webpack 대비 압도적으로 빠른 로컬 서버 구동 및 빌드 속도를 제공하며, 로컬 프록시 설정이 직관적이어서 도입했다.
* **React Router**: 사용자와 관리자의 접근 권한을 분리하고, 중첩 라우팅을 통해 레이아웃을 효율적으로 관리하기 위해 사용했다.

---

## 2. 확장성을 고려한 프로젝트 아키텍처

### 공통 디자인 시스템 선구축

기획 초반에는 상세 디자인이 없었다. 페이지별로 즉시 퍼블리싱을 시작하면 폰트 크기, 여백, 버튼 스타일이 파편화될 위험이 컸다. 이를 방지하기 위해 테마(네이비 계열 색상), 타이포그래피, 폼 요소, 공통 레이아웃 등의 기준을 먼저 정의하고 컴포넌트화했다.

### 디렉터리 구조와 책임 분리

하나의 파일에 UI 렌더링, API 호출, 비즈니스 로직이 섞이지 않도록 역할을 기준으로 폴더를 분리했다.

```text
src/
  api/        # 서버 통신 함수
  components/ # 공통 UI 및 레이아웃
  contexts/   # 전역 상태 (사용자 세션 등)
  mocks/      # API 연동 전 임시 데이터
  pages/      # 라우트 단위 화면
  utils/      # 계산 및 포맷팅 로직

```

특히 독서마라톤의 핵심인 '독서한 책 1쪽을 5m로 환산해 누적 거리와 완주율 계산' 로직은 컴포넌트 내부에 두지 않고 `utils/reading.ts`로 분리했다. 이를 통해 독서일지, 나의 현황, 관리자 대시보드 등 여러 페이지에서 동일한 계산 로직을 공유하고, 향후 환산 기준(예: 1쪽당 10m)이 변경될 때 한 곳만 수정하면 되도록 구성했다.

## 3. Trouble Shooting

개발 및 배포 과정에서 직면한 주요 문제들과 해결 과정이다.

### Issue 1. `.gitignore` 패턴 충돌로 인한 파일 누락

**현상:** 로컬 환경에서는 독서 기록 모킹 데이터가 정상적으로 동작했으나, 원격 저장소(GitHub)에는 해당 파일들이 올라가지 않는 문제가 발생했다.
**원인:** `.gitignore`에 로그 파일을 제외하기 위해 작성한 `logs`라는 광범위한 규칙이 `src/mocks/readingLogs.ts` 파일의 경로명 패턴과 충돌하여 Git 추적에서 제외되었다.
**해결:** `.gitignore` 규칙을 `*.log` 또는 특정 디렉터리(`/logs/`)로 구체화했다. 누락된 파일을 복구한 뒤 `git ls-tree -r origin/main --name-only` 명령어를 통해 원격 저장소에 파일이 정상적으로 포함되었는지 직접 확인하는 검증 단계를 거쳤다.

### Issue 2. 환경에 따른 빌드 실패 (Case Sensitivity)

**현상:** 로컬(Windows/Mac) 환경에서는 `npm run build`가 성공했으나, CI/CD 환경(Linux 기반) 및 다른 팀원의 깨끗한 환경에서는 빌드 에러가 발생했다.
**원인:** 컴포넌트 import 경로의 대소문자 오타가 원인이었다. Windows나 Mac의 기본 파일 시스템은 대소문자를 엄격하게 구분하지 않지만, 배포 서버인 Linux 환경에서는 이를 다른 파일로 인식하여 모듈을 찾지 못했다.
**해결:** import 경로의 대소문자를 파일명과 정확히 일치하도록 수정했다. 이후 로컬에서 성공하더라도 반드시 캐시가 없는 깨끗한 컨테이너 환경에서 빌드 테스트를 수행하는 규칙을 세웠다.

### Issue 3. 프록시 설정과 CORS 정책 충돌

**현상:** 로컬 개발 환경에서는 Vite의 proxy 설정을 통해 백엔드(`localhost:8080`)와 정상적으로 통신했으나, 운영 환경(Docker 기반 프론트엔드와 AWS 백엔드 분리)에 배포한 후 CORS 에러가 발생했다.
**원인:** 개발 환경에서는 Vite가 브라우저를 속여 같은 출처(Origin)인 것처럼 요청을 프록시 처리해주지만, 배포 환경에서는 브라우저가 프론트엔드와 백엔드의 도메인을 다른 출처로 인식하기 때문이다.
**해결:**
환경 변수를 분리하여 로컬과 배포 환경의 네트워크 흐름을 명확히 구분했다.

* **로컬:** `VITE_API_PROXY_TARGET`을 활용해 프록시 서버를 경유하도록 설정.
* **운영:** 백엔드 서버의 설정(Spring Security/CORS Filter)에 프론트엔드의 운영 도메인을 Allowed Origin으로 명시적으로 추가하도록 백엔드 개발자에게 요청했다. 에러 발생 시 브라우저 콘솔의 에러 문구에만 의존하지 않고, Network 탭에서 실제 Request URL과 헤더를 분석하여 원인을 교차 검증했다.

## 4. 운영을 고려한 단독 개발 전략

프론트엔드 개발자가 혼자일수록 코드의 품질과 협업 프로세스를 엄격하게 관리해야 했다.

* **브랜치 분리:** 단독 개발임에도 `main`(배포), `develop`(통합), `feat/*`(기능 개발) 브랜치를 분리하여 작업했다. 이슈 발생 시 롤백과 원인 파악을 쉽게 하기 위함이다.
* **기록의 습관화:** API 명세가 나오기 전 화면 흐름부터 선행 개발했기 때문에, 컴포넌트 내부에 '백엔드와 확정이 필요한 임시 값(상태 코드, 날짜 포맷 등)'을 주석과 문서로 남겼다.
* **관리자 경험(UX) 고려:** 관리자 화면은 단순히 데이터를 보여주는 것을 넘어 업무 효율성을 높여야 한다. 반려/승인 등의 다중 선택 기능, 필터링, 그리고 자주 쓰는 작업과 위험한 작업(삭제 등)의 시각적 위계를 명확히 분리하여 설계했다.

## 요약

이 프로젝트를 통해 프론트엔드 개발은 단순히 화면을 그리는 작업이 아님을 다시 확인했다. 확정되지 않은 정책 사이에서 변동성을 수용할 수 있는 아키텍처를 설계하고, 로컬 환경의 성공을 맹신하지 않으며, 실제 배포 환경의 네트워크 흐름(CORS, Proxy)까지 통제할 수 있어야 안정적인 서비스 운영이 가능하다.
