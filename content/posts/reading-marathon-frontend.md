한국외국어대학교 글로벌캠퍼스 도서관의 독서마라톤 웹서비스 프론트엔드를 혼자 맡게 되었다. 단순한 개인 프로젝트가 아니라 실제로 다음 기수에도 계속 사용할 서비스라는 점에서, 화면을 만드는 기준부터 달라야 했다.

## 디자인이 없는 페이지부터 시작하기

처음에는 메인 화면의 방향만 있고 로그인, 참가 신청, 마이페이지, 관리자 화면의 상세 디자인은 정해지지 않았다.

이럴 때 바로 세부 스타일을 만들면 페이지마다 기준이 달라질 수 있다. 먼저 다음 요소를 공통 규칙으로 정리했다.

- 도서관 사이트와 어울리는 차분한 네이비 색상
- 제목, 본문, 안내 문구의 글자 크기와 굵기
- 입력 폼과 버튼의 높이 및 간격
- 헤더와 푸터를 포함한 공통 레이아웃
- 모바일에서도 무너지지 않는 최대 너비

기준을 먼저 만든 뒤 각 페이지를 구현하니 로그인과 회원가입처럼 비슷한 화면을 맞추는 작업도 수월해졌다.

## 데이터 구조를 모르는 상태에서 어디까지 만들 수 있을까

API 명세와 ERD가 완성되기 전에도 정적인 화면과 사용자 흐름은 구현할 수 있었다. 다만 참가 신청, 로그인, 독서 기록처럼 데이터의 기준이 중요한 화면은 임시 값을 코드 곳곳에 넣지 않도록 주의했다.

화면 컴포넌트와 데이터 처리 영역을 분리하고, 실제 API가 연결될 자리를 명확히 남겼다. 이후 API 주소가 확정됐을 때 UI 전체를 다시 만들지 않고 요청 함수만 연결할 수 있도록 하기 위해서였다.

## 혼자 개발할수록 기록이 필요했다

프론트엔드 담당자가 한 명이면 빠르게 결정할 수 있지만, 잘못된 방향도 혼자 오래 끌고 갈 수 있다. 그래서 다음 내용을 짧게라도 남겼다.

1. 지금 구현한 범위
2. 아직 임시 데이터인 부분
3. 백엔드와 확인해야 할 값
4. 디자인 변경 시 함께 수정해야 하는 파일

이 기록은 다른 팀원에게 상황을 공유할 때뿐 아니라, 며칠 뒤 다시 코드를 볼 때도 도움이 됐다.

## 배운 점

단독 개발은 모든 코드를 혼자 작성하는 경험이기도 하지만, 정해지지 않은 내용을 구분하고 질문하는 경험에 더 가까웠다.

앞으로는 화면 완성도뿐 아니라 접근성, 컴포넌트의 책임, API 오류 상태까지 같은 기준으로 점검하며 서비스를 마무리하려 한다.
